# BCM2712 research entry

Profiles: [module](../boards/bcm2712-cm5/README.md), [SBC](../boards/bcm2712-rpi5/README.md).
Both use the BCM2712 family. RP1 is a separate I/O component.
The module and SBC expose different connectors and boot-storage choices.

Use the [module datasheet](https://datasheets.raspberrypi.com/cm5/cm5-datasheet.pdf) for module design constraints.
Use the exact board's firmware and EmberBSD documentation for ACPI, clocks, DMA and peripheral drivers.
The [V3D implementation](https://github.com/oxtech-ember/EmberBSD/blob/main/sys/arch/arm/broadcom/docs/bcm2712-v3d.md)
and [validation](https://github.com/oxtech-ember/EmberBSD/blob/main/sys/external/bsd/drm2/bcmv3d/docs/bcm2712-v3d-validation.md) have separate scopes.

On CM5, a bounded [Plasma Desktop scenario](https://github.com/oxtech-ember/EmberBSD-Ports/blob/82308f7eaaeba4772df06f3798cb20353630e440/probes/plasma-mobile/toolkit/tests/plasma-desktop/README.md#physical-cm5-acceptance) uses hardware V3D on a virtual output.
Full login, physical KMS/HDMI, hotplug and sustained desktop use remain unaccepted.
A virtual output is not a monitor signal.
A CM5 GPU result does not validate display wiring on a custom carrier or the SBC.
Keep silicon stepping, module revision and firmware revision as separate fields.
Source IDs: `cm5-datasheet`, `os-cm5`, `os-rpi5`, `os-v3d`, `ports-plasma-desktop` in [sources.json](../sources.json).
